# ルート自動入力 設計書

作成日: 2026-09-02

## 1. 目的

訪問予定の患者を登録しておき、その日に回る患者を選んで訪問順を整え、Googleマップの経路画面へ渡す。
毎回住所を手入力する手間をなくすことが狙い。

利用端末はiPad。iPadのSafariで開くPWA(ホーム画面に追加できるWebアプリ)として実装する。

## 2. 制約

- **Macを用意できない。** iOSアプリのビルドと署名はmacOS上でしか行えないため、SwiftUI/Xcodeによるネイティブアプリ開発、およびExpoを含むあらゆるネイティブiOSビルドは選択できない。この制約からPWAを採用する。
- **費用をかけない。** Apple Developer Program(年額)、Google Maps Platform APIキー、サーバー利用料のいずれも発生させない。
- **患者情報を端末外へ出さない。** サーバー送信、分析SDK、外部APIへの問い合わせ、コンソールログへの氏名・住所の出力をいずれも行わない。ネットワーク通信は、ユーザーが明示的に「Googleマップで開く」を押したときの遷移のみ。

## 3. スコープ

### 実装するもの

- 患者(氏名・住所)の登録・編集・削除・検索
- 患者の複数選択(1〜10件)
- 選択した患者の訪問順の並べ替え
- Googleマップ経路URLの生成と起動
- 経由地の上限を超える人数を選んだ場合のルート自動分割
- データのエクスポート/インポート(JSONファイル)
- ホーム画面へ追加できるPWA化(オフラインでも画面が開く)

### 実装しないもの

| 項目 | 理由 |
|---|---|
| 訪問順の自動最適化 | ユーザー指定順を維持する方針。Googleマップ側の最適化にも委ねない |
| 住所入力のサジェスト | Google Places APIはAPIキーと課金が必要。MapKit相当の無料手段はWebにない |
| 複数端末間の同期 | サーバーが必要になる。端末間の移動はエクスポート/インポートで代替する |
| アプリ独自のPINロック | iPad本体のパスコード/Face IDで足りると判断 |
| 電話番号・メモ等の追加項目 | 初版は氏名・住所のみ。後から項目を足せるデータ構造にしておく |

## 4. 技術構成

| 要素 | 選定 | 理由 |
|---|---|---|
| ビルド | Vite + TypeScript | 静的ファイルを出力するだけでGitHub Pagesに載る。型で入力検証の取りこぼしを防ぐ |
| UI | フレームワークなし(素のDOM操作) | 画面数が4つと少なく、Reactを入れるほどの複雑さがない |
| 保存 | IndexedDB(`idb`ライブラリ) | 件数が増えても扱え、容量上限がlocalStorageより緩い。`idb`は依存として十分小さい |
| テスト | Vitest | Viteと同じ設定で動く |
| 配布 | GitHub Pages | 無料。ユーザーがGitHubアカウントを保有済み |

リポジトリ名/フォルダ名は`route-auto-input`。PWAの表示名(ホーム画面のアイコン名)は「ルート自動入力」とする。

## 5. データモデル

```ts
type Patient = {
  id: string;        // crypto.randomUUID()
  name: string;      // 氏名
  address: string;   // 住所(手入力)
  createdAt: string; // ISO 8601
  updatedAt: string; // ISO 8601
};
```

IndexedDB: DB名`route-auto-input`、オブジェクトストア`patients`、キー`id`。

エクスポート形式(JSONファイル):

```json
{
  "version": 1,
  "exportedAt": "2026-09-02T12:00:00.000Z",
  "patients": [ /* Patient[] */ ]
}
```

`version`は将来項目を追加したときの移行判定に使う。インポート時は`version`と各レコードの必須項目を検証し、不正なファイルは取り込まずにエラーを表示する。

## 6. 画面構成

### 6.1 患者一覧(初期画面)

- 登録済み患者を登録順(新しいものが上)に表示。各行に氏名・住所・選択チェックボックス・編集・削除。氏名順の並べ替えは、漢字の氏名を読み仮名なしでは日本語として正しく並べられないため初版では行わない。
- 検索欄(氏名・住所の部分一致)で絞り込み。
- 「+ 新規登録」ボタン。
- 選択件数を常時表示し、11件目のチェックは受け付けない(上限に達したら未選択のチェックボックスを無効化し、理由を表示)。
- 1件以上選択されると「次へ(順番を決める)」ボタンが有効になる。

### 6.2 登録/編集フォーム

- 氏名・住所の入力欄。どちらも必須。前後の空白は保存時に除去する。
- 住所のサジェストはなし(手入力)。入力補助として「この住所をGoogleマップで確認」リンクを置き、`https://www.google.com/maps/search/?api=1&query=<住所>`を別タブで開いて表記の正しさを確認できるようにする。
- 保存/キャンセル。

### 6.3 訪問順の並べ替え

- 選択した患者を縦一列に表示。各行に上へ/下へボタン(iPadのSafariではドラッグ操作の実装が不安定になりやすいため、上下ボタンを主操作とする)。
- 先頭が出発地、末尾が到着地、その間が経由地であることを画面上に明示する。
- 選択件数が`MAX_STOPS_PER_ROUTE`以内なら「Googleマップで開く」ボタンを1つ表示する。
- 超える場合は§7.3の規則でルートを分割し、「ルート1を開く」「ルート2を開く」…と分割数ぶんのボタンを順に表示する。各ボタンには含まれる患者名を併記する。一度開いたボタンには印を付け、どこまで進んだかがわかるようにする(印は画面を離れるまでの一時的な状態でよい)。

### 6.4 設定

- エクスポート: 現在の全患者データをJSONファイルとしてダウンロード。
- インポート: JSONファイルを選び、**全置換**か**追記(既存idは上書き、新規idは追加)**かを選んでから実行する。実行前に件数を提示して確認を取る。

## 7. Googleマップ連携

`src/googleMapsUrl.ts`に純関数として実装し、UIから切り離してテストする。

### 7.1 生成規則

1本のルートに含まれる地点が2件以上のとき(経路):

```
https://www.google.com/maps/dir/?api=1
  &origin=<先頭の住所>
  &destination=<末尾の住所>
  &waypoints=<間の住所を | で連結>
  &travelmode=driving
```

地点が1件のとき(経路が成立しないため地点検索として開く):

```
https://www.google.com/maps/search/?api=1&query=<住所>
```

- URLの組み立ては`URL`と`URLSearchParams`で行い、手作業のパーセントエンコードはしない(日本語住所と空白を壊さないため)。
- 遷移は`window.location.href`への代入で行う。iPadにGoogleマップアプリが入っていればアプリが開き、なければSafariでWeb版が開く。どちらの場合もこちらから制御はしない。
- Googleマップから元アプリへ自動で戻ることは期待しない仕様とする。

### 7.2 経由地の上限

Google Maps URLsの公式ドキュメントには次の記載がある。

> The number of waypoints allowed varies by the platform where the link opens, with up to three waypoints supported on mobile browsers, and a maximum of nine waypoints supported otherwise.

つまり経由地の上限は、リンクが開かれる先がモバイルブラウザなら3件、それ以外なら9件となる。iPadのSafariは既定でデスクトップ版として振る舞い、またGoogleマップアプリがインストールされていればアプリ側で開かれるため、**iPadで実際にどちらが適用されるかは実機で確認するまで確定できない。**

この不確実性を設計で吸収するため、1本のルートに含められる地点数を定数`MAX_STOPS_PER_ROUTE`として1か所に定義する。

- **初期値は5**(出発地1 + 経由地3 + 到着地1)。上限が厳しい側に倒れても確実に動く値。
- 実機確認(§10)で経由地9件が通ることが確認できたら、この定数を10に変更する。これだけで分割は起きなくなる。

### 7.3 ルート分割

選択件数が`MAX_STOPS_PER_ROUTE`を超える場合、順番を保ったまま複数のルートへ分割する。分割の境目となる患者は前後どちらのルートにも含め、経路が途切れないようにする。

- ルート1は先頭から`MAX_STOPS_PER_ROUTE`件。
- 次のルートは、前のルートの最後の患者から始めて`MAX_STOPS_PER_ROUTE`件。
- 分割数は `ceil((選択件数 - 1) / (MAX_STOPS_PER_ROUTE - 1))` 本。

例(`MAX_STOPS_PER_ROUTE`=5、10人選択時、患者を1〜10と表記):

| ルート | 含まれる患者 |
|---|---|
| ルート1 | 1, 2, 3, 4, 5 |
| ルート2 | 5, 6, 7, 8, 9 |
| ルート3 | 9, 10 |

最後のルートが1件だけになることはない(必ず前のルートの最終地点を含むため、最小でも2件)。

分割は純関数`splitIntoRoutes(stops, maxStopsPerRoute)`として実装し、UIから切り離してテストする。

### 7.4 検証(URL生成前)

| 条件 | 挙動 |
|---|---|
| 選択0件 | ボタン無効 |
| 選択11件以上 | そもそも選択させない(6.1) |
| 住所が空 | 保存時に弾いているため通常は起きない。防御的に検出したらエラー表示 |
| 同一住所が複数 | 警告を出し、ユーザーが「このまま開く」を選べば続行(同一施設内の別患者がありうるため、ブロックはしない) |

## 8. エラーハンドリング

- 検証エラーは画面上部のメッセージ領域に日本語で表示する。alertは使わない。
- IndexedDBの読み書き失敗時は「データを保存できませんでした」と表示し、入力内容は画面に残す。
- エラーメッセージに氏名・住所を含めない(表示は画面上の該当行で示す)。

## 9. アクセシビリティ

- タップ領域は44px以上。
- 文字サイズは`rem`指定とし、OSの文字サイズ設定に追従させる。
- チェックボックス・ボタンにラベルを付け、VoiceOverで何の患者の操作かがわかるようにする。

## 10. テスト

### 自動テスト(Vitest)

- URL生成: 2件/3件/5件、1件のときの検索URL、日本語住所、空白を含む住所、記号を含む住所のエンコード。
- ルート分割`splitIntoRoutes`: 上限ちょうど(5件)は分割しない、6件は2本、10件は3本、境目の患者が前後のルートに含まれる、各ルートが2件以上になる、上限を10に変えると10件が1本になる。
- 検証ロジック: 0件、11件、空住所、重複住所。
- エクスポート/インポート: 書き出したJSONを読み込むと同じデータに戻ること(往復)、壊れたJSON・version違いを弾くこと。

### 手動確認(iPad実機)

1. Safariでページを開き「ホーム画面に追加」ができる
2. ホーム画面のアイコンから起動し、氏名・住所を登録できる
3. Safariを完全に閉じて再起動してもデータが残っている
4. 2件選択→順番を入れ替え→Googleマップアプリが正しい経路で開く
5. **経由地の上限確認(最重要)**: 10件選択して分割されたルートがそれぞれ正しく開く。あわせて、手作業で経由地9件のURLをiPadのSafariに貼り付け、Googleマップが11地点の経路を表示できるか確認する。表示できる場合は`MAX_STOPS_PER_ROUTE`を10に変更し、10件が1本のルートで開くことを再確認する
6. Googleマップアプリを削除した状態でもWeb版が開く(このときは経由地3件が上限になる可能性があるため、上限を10に引き上げていた場合は挙動を再確認する)
7. エクスポートしたファイルをインポートし直すと同じ一覧に戻る
8. 機内モードでもアプリ画面自体は開く(オフラインキャッシュ)

## 11. 配布

1. `route-auto-input`をGitHubのリポジトリとして公開する。
2. GitHub Actionsで`npm run build`し、`dist`をGitHub Pagesへデプロイする。
3. iPadのSafariで公開URLを開き、共有メニューから「ホーム画面に追加」。

公開されるのはアプリの画面(空の状態)のみで、患者データが公開されることはない。データはiPad内のIndexedDBにのみ存在する。

## 12. 将来拡張

- 電話番号・メモなどの項目追加(`version`を上げてインポート時に移行)
- 訪問先のグループ分け(曜日別・地域別)
- 11件以上の選択(分割の仕組みは§7.3で用意済みのため、選択上限を緩めるだけで対応できる)
